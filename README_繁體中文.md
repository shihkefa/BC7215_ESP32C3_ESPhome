# BC7215A＋ESP32-C3-MINI-1 雙 Type-C 開發板 — ESPHome v1.0.10

本版依使用者要求，回到 v1.0.7 配對規則並更新原廠碼庫至 V8.1 build 2632。
請先閱讀「碼庫更新說明.md」，下方 v1.0.7 及更早章節為功能與歷史說明；
其中關於舊碼庫升級免重配、冷氣名稱實體的描述不適用於本版。

開始配對 → 原廠遙控器冷房 25°C 按風速鍵 → 保存匹配 → 實機確認。
不含 v1.0.8／v1.0.9 的候選自動發射掃描，保留「下一個匹配」按鈕。
已移除「冷氣名稱_Label」實體。SHT40、RGB、擺風學習／同步與 GPIO 接線沿用 v1.0.7。

本版以使用者指定的 ESP32-C3-MINI-1 模組開發板為目標，沿用 v1.0.1 的 HA 空調、配對、
原廠遙控器同步、匹配保存、UART 診斷與手動重試。尚未刷入新板；驗證狀態見 `VALIDATION.md`。

## v1.0.7 遙控器擺風同步

v1.0.6 只有學習／發送，收到遙控訊號時將擺風標為未知。本版增加已學習樣本的辨識：
在記憶體內把收到的完整封包與各方向的關／開樣本，分別交給碼庫產生冷房 25°C、自動風、
相同按鍵的封包，再比較有效資料及格式。這會消除正常設定及其校驗碼的差異，**不發射紅外線**。

- 唯一吻合關閉／上下／左右時，更新空調實體的擺風選項。
- 「擺風狀態」會顯示「依遙控樣本辨識」，仍不是冷氣主機回報。
- 完整比對不吻合、多方向歧義、開關差異被碼庫消除、收到關機或無法解析時，標示未知。
  ESPHome 擺風沒有未知選項，所以空調選單保留上次選擇，請搭配擺風狀態感測器判讀。
- 不以猜測的差異位元、模糊相似度或單次切換推定擺風。遙控器計數器、其他附加設定、
  不同按鍵格式等仍可能導致無法辨識；不保證所有品牌都能同步。
- 未學習的方向，以及兩軸同時開的狀態，無法據此可靠辨識。
- 比對結束恢復剛收到的完整封包，不把比對用的 25°C 套用到下一個控制指令。
- 沿用 v1.0.6 已保存的配對與擺風資料，通常不需要重新學習；SHT40、RGB、接線不變。

更新後先用原廠遙控器切換已學習方向的開／關，再改為 28°C 重試；確認 HA 擺風及溫度同時跟隨。
若未同步，查看「擺風狀態」及 DEBUG 日誌 `Swing RX`：state=-1 未知，0 關閉，1 上下，2 左右。
若沒有這行日誌，也請保留鄰近的 `IR RX`／解析失敗訊息，便於判斷是否收到適用的完整碼。

## v1.0.6 上下／左右分開學習擺風（歷史）

新增「學習上下擺風」「學習左右擺風」「擷取擺風樣本」「取消擺風學習」按鈕，
以及各方向的學習狀態與擺風狀態感測器。原本的 SHT40、接線、配對識別與保存功能沿用。

**操作方式請先看 [擺風學習操作.md](擺風學習操作.md)。**
每個方向擷取擺風關／開兩筆完整訊號，另一方向保持關閉。
以原廠 `bc7215_ac_replace_base()` 載入樣本，再用碼庫產生當下溫度、模式與風速的指令。
本功能不是碼庫自動回報擺風支援能力；學習成功後仍需確認葉片實際動作。

空調固定顯示關閉／上下／左右選項，未學習的方向會拒絕發送。
選擇上下時左右關閉，選擇左右時上下關閉；沒有兩方向同時開啟的選項。
資料各自保存，綁定配對指紋；取消或逾時不覆蓋舊樣本。
收到原廠遙控器後，溫度／模式／風速照常同步；擺風改標未知，因碼庫沒有提供此欄位解析。

RGB 在一般配對、補充取樣與擺風學習時七彩循環，其他階段關閉。
使用的是另外 2,076 bytes 的擺風偏好資料，原本 4,420 bytes 的 PairingData 不更動。
主機測試已通過；尚未執行完整 C3 目標韌體編譯、實機擺風或刷寫，不附 BIN。

## v1.0.5 SHT40 室內溫濕度

使用 ESPHome 內建 sht4x 元件。HA 新增「室內溫度_Temperature」及「室內濕度_Humidity」，
每 30 秒更新，顯示一位小數；顯示位數不代表感測器的實際精度。

| SHT40 模組 | C3 開發板 |
|---|---|
| VCC／VIN | 3V3 |
| GND | GND |
| SDA | GPIO4 |
| SCL | GPIO5 |

適用支援 3.3V 供電與邏輯的 SHT40 I²C 模組；使用模組上的 SDA／SCL 上拉電阻。
BC7215A 維持 MOD GPIO0、BUSY GPIO1、RX GPIO2、TX GPIO3；板載彩燈維持 GPIO8。

- I²C 使用 100kHz，啟動掃描開啟，預設感測器位址 0x44。
- 高精度量測，內建加熱器關閉，避免加熱干擾一般室內溫濕度讀值。
- 感測器應保持通風並遠離 C3、穩壓器等熱源；不要緊貼發熱元件。
- 刷入後先查看日誌有沒有掃描到 0x44，再確認 HA 的溫濕度實體有讀值。
  尚未接上感測器會出現 I²C／SHT4X 初始化錯誤，請接好後重新啟動。
- 溫濕度以獨立感測器實體顯示，本版未加入依室溫自動開關冷氣的控制規則。

升級請替換 YAML 與 components/bc7215a，保留自己的 secrets 與 logger_uart 設定。
[ESPHome SHT4X 說明](https://esphome.io/components/sensor/sht4x/)

## v1.0.4 板載 RGB 配對指示燈

依使用者照片的雙 Type-C、排針與元件佈局，比對 YD-ESP32-C3-COREBOARD；
該板原理圖的 U6 為 XL-5050RGBC-WS2812B，經 RGB 跳線接 GPIO8。
照片本身不能證實所有批次的電氣接線，本包依此比對採 GPIO8、WS2812、GRB、1 顆。
[VCC-GND 原理圖（經銷商提供）](https://sklep.msalamon.pl/download/39155/?tmstv=1682598657)

- 正常待機、紅外收發、通訊探測、故障、未配對等待：彩燈熄滅。
- 自動／手動配對、補充取樣及擺風學習：20% 亮度七彩循環。
- 配對／學習完成、取消或逾時：退出燈效，通常於下一次 100ms 狀態檢查熄滅。
- 配對狀態直接取自元件，不使用 HA 連線狀態或狀態訊息文字判斷。
- 燈光使用 internal: true，不在 HA 建立可手動開啟的燈實體。
- restore_mode: ALWAYS_OFF，應用程式啟動時不恢復上次燈效；也加入關機熄燈動作。
  韌體尚未接管時的上電／重置瞬間燈光仍需實機確認。
- 無舊配對可恢復時按取消，改為真正退出配對並等待「開始配對」；不清除既有保存資料。
  沒有有效配對的下次開機仍會自動進入配對模式。
- GPIO8 保留給板載 RGB，BC7215A 接線仍為 GPIO0／1／2／3；BC7215A 板上的指示燈電路不受此設定控制。

若板子有不同接線，可在 substitutions 的 rgb_pin 修改；不要猜測改到正在使用的 UART 腳位。
此包尚未刷入，請在實機依序驗證待機熄燈、開始配對變色、取消熄燈與成功配對熄燈。
使用原生 USB 日誌者，保留自己的 logger_uart: USB_SERIAL_JTAG 設定。

## v1.0.3 名稱、識別碼與候選數量

- HA 新增可編輯的「冷氣名稱_Label」，例如「客廳－大金」。它是獨立文字欄位，
  不會自動修改 HA 空調卡片或裝置名稱；也不會改動配對或發射紅外線。
- 名稱使用 ESPHome 的 restore_value 保存；依預設寫入週期，修改後請等至少一分鐘再拔電。
  名稱上限為 96 UTF-8 bytes，純中文字建議不超過 32 字。重新配對不會自動清除名稱。
- 「配對資料識別碼_PairingID」顯示如 `P-A83F92C1`（示意值），由已保存的配對資料、
  候選序號及碼庫版本計算。相同保存資料在重啟後得到相同識別碼；一般調溫、同步及改名稱不影響它。
  換候選、重新取樣或更換碼庫版本可能改變識別碼。
- 此碼採用 32-bit FNV-1a 短雜湊，可能碰撞；它不是唯一序號、品牌辨識結果或官方碼庫編號，
  不能只憑這個短碼恢復配對。實際恢復仍使用原有完整配對資料。
- 「候選序號_Match」顯示如「候選 01／共 03 個」。總數是本次基礎取樣通過原廠初步匹配的
  候選數，不是整個品牌的碼庫總數，也不表示所有候選都已經補充取樣或實測成功。
- 配對完成、開機恢復與取消配對恢復時，程式會計算候選並恢復原選擇與補充樣本。
  計數只運算碼庫，不發射紅外線。達到掃描上限／時間限制時顯示「至少 N 個」，不假報精確總數。
- 配對中顯示「配對中」；保存失敗顯示「未保存」，並保留原有狀態錯誤提示。

升級：替換 YAML 與整個 `components/bc7215a` 資料夾，保留自己的 secrets 與 logger_uart 設定。
GPIO 接線沿用 RX GPIO2、TX GPIO3、MOD GPIO0、BUSY GPIO1。
配對資料結構與儲存鍵不變，同一裝置一般升級不需重新配對；本次未執行刷入。
舊「匹配編號_Match」改名後，HA 可能保留舊實體為不可用，請以新的「候選序號_Match」為準。

## 新板設定與雙 USB 插孔

- 板型：`esp32-c3-devkitm-1`；Arduino framework；使用 4MB Flash 配置。
- ESP32-C3-MINI-1 是模組名稱，不足以唯一識別載板。此包採標準 GPIO 編號，兩個插孔的
  實際位置／標示請依載板確認，不以左／右位置猜測。
- 預設 `logger_uart: UART0`：接 USB 轉串口晶片的插孔，常標為 UART／COM。
  ESPHome 應用日誌為 115200、8N1，使用 C3 GPIO21 TX／GPIO20 RX。
- 如要從原生 USB 插孔讀日誌，將 substitutions 的 `logger_uart` 改為 `USB_SERIAL_JTAG`
  後重新編譯；此介面使用 GPIO18／GPIO19。本設定只選擇應用日誌輸出，不表示另一插孔不能燒錄。
- GPIO20／21 及 GPIO18／19 保留給 USB／日誌用途；BC7215A 使用下面列出的 GPIO0／1／2／3。
- 預設關閉 Wi-Fi 省電 `power_save_mode: none`，並增加 SSID、BSSID 與 MAC 診斷實體。
  保留 DHCP，不固定到舊板的 192.168.1.143，也不鎖定之前的基地台 BSSID；連線品質仍需新板實測。

[ESPHome Logger 的 C3 引腳及介面說明](https://esphome.io/components/logger/)；
[ESPHome Wi-Fi 省電設定](https://esphome.io/components/wifi/#power-save-mode)。

這是 ESPHome 外部元件，不是 Arduino IDE 程式。YAML 的 `framework: type: arduino`
只是選用 ESPHome 底層編譯框架，目的是使用原廠 Arduino 驅動；編譯、燒錄、日誌、OTA
及 HA 整合仍由 ESPHome 管理。不需要 MQTT。

## 接線（依你的實際配置）

| BC7215A | C3-MINI-1 開發板的 GPIO／電源 |
|---|---|
| VCC | 3V3 |
| GND | GND |
| MOD | GPIO0 |
| BUSY | GPIO1 |
| TX | GPIO2（ESP 接收） |
| RX | GPIO3（ESP 發送） |

模組與 C3 共地，以 USB-C 供電；此接法讓 BC7215A 使用 3.3V。串口設定為 **19200、8N2**。
本次 UART RX 由 GPIO4 改到 GPIO2，請將 BC7215A TX 接線一起移到 GPIO2。
ESPHome 會提示 GPIO2 是 strapping pin；換線後需確認斷電再上電可正常啟動。
不要把 YAML 的 stop_bits 改成 1。模組不需要額外接 remote_receiver 或 remote_transmitter。

## 安裝

1. 使用 **ESPHome 2026.8.2**。首次交付以此版本驗證；其他版本可能需要調整。
2. 將 `bc7215a-c3.yaml` 放到你的 ESPHome 設定資料夾。
3. 將整個 `components/bc7215a` 資料夾放到同一設定資料夾的 `components` 底下。
   例如 HA ESPHome 常用的位置是 `/config/esphome/components/bc7215a/`，
   YAML 則在 `/config/esphome/bc7215a-c3.yaml`。
   必須保留資料夾裡全部檔案，包括 `.c`、`.cpp`、`.h` 和 `.py`；只貼 YAML 不夠。
4. 開啟 `secrets.example.yaml`，把需要的項目合併到你原有的 `secrets.yaml`。
   填入 `wifi_ssid`、`wifi_password`（2.4GHz Wi-Fi）及 `ap_password`（備援 AP 密碼）。
   **不要直接覆蓋你原本的 secrets.yaml。**
5. 在 ESPHome 按 Install，第一次透過 USB 燒錄；之後可用 ESPHome OTA。
   C3 如果無法進入下載模式，可先按住 BOOT 再連接 USB，連線後放開。
6. HA「設定 → 裝置與服務」加入發現的 ESPHome 裝置。
   沒有自動發現時，可輸入裝置 IP；這份設定未使用 API 加密金鑰。
7. 開啟 ESPHome Logs。預設使用 USB 轉串口端的 UART0；BC7215A 使用另一個硬體 UART，
   指定 GPIO3／2，與日誌分開。若接原生 USB 讀日誌，先依上節切換 logger_uart。

命令列也可以：

```bash
esphome config bc7215a-c3.yaml
esphome compile bc7215a-c3.yaml
esphome run bc7215a-c3.yaml
```

## 第一次配對

沒有已保存的配對時，開機會自動進入配對。你也可以在 HA 按「開始配對_Pair」。

1. 把原廠遙控器設成 **冷房、25°C**。
2. 對準 BC7215A 的黑色接收頭，短按一次 **風速鍵**，保持冷房 25°C。
3. 觀察「運作狀態_Status」及日誌。配對成功會顯示已保存。
4. 若提示補充取樣，依提示操作。準備溫度／模式時先遮住遙控器發射頭，
   只讓最後一次回到「冷房25°C」的目標按鍵訊號送到模組，避免先收到準備中的指令。
5. 用原廠遙控器改成 26°C，確認 HA 的設定溫度跟著改。
6. 在 HA 改成 27°C，確認冷氣收到指令。
7. 分別測試開關、模式與各段風速。匹配成功不等於每一項功能都已實機驗證。

若配對成功但操作不對，可按「下一個匹配_NextMatch」，再測試。
若沒有下一個匹配，會保留原匹配。進入重新配對後，「取消配對_CancelPair」
可恢復最後一次成功保存的配對。新配對成功後會取代原配對。

| 實體 | 說明 |
|---|---|
| 空調_AC | 電源、16–30°C 設定溫度、自動／冷房／暖房／除濕／送風、四段風速 |
| 已配對_Paired | 是否已有可用配對 |
| 冷氣名稱_Label | 可編輯、保存的名稱，例如「客廳－大金」 |
| 配對資料識別碼_PairingID | 保存配對資料的短雜湊，例如 P-A83F92C1；不是官方碼庫編號 |
| 候選序號_Match | 例如「候選 01／共 03 個」；本次取樣的候選位置與總數 |
| 碼庫版本_LibraryVersion | 實際原廠碼庫版本 |
| 運作狀態_Status | 配對提示、接收與發射結果、故障說明 |
| 本次已同步_StateKnown | 本次開機後是否取得電源資訊，或完成一個控制指令 |
| 開始配對／下一個匹配／取消配對 | 配對操作 |
| 重新啟動、連線狀態、Wi-Fi訊號、IP、運作時間 | 維護資訊 |

**候選序號不是品牌型號，也不是跨裝置通用的碼庫編號。** 原廠自動配對 API
沒有提供目前匹配的品牌／機型名稱。本程式保存候選順序與配對樣本，並重新計算候選總數。
另一個遙控器的「候選 01」可能代表不同協議，請使用自訂名稱及配對資料識別碼區分。

## 狀態與保存

- 接收原廠遙控器後，只更新 HA，不再次發射。
- 關機時單獨調整溫度或風速，只更新準備使用的設定，不發送開機指令。
- 從關機切換成冷房等模式時，先發送開機，再發送指定設定。
- 發射中的 HA 操作會合併成最新的待送設定，完成前一個指令後再送。
- Wi-Fi 或 HA 離線時仍持續接收、更新本機狀態；重連由 ESPHome API 同步。
- 配對資料包含收到的全部樣本段、格式與匹配順序，只在配對完成時寫入內部 Flash。
- 重啟僅載入配對與最後顯示狀態，**不自動發射**。
- 重啟後「本次已同步」為否，避免把保存的狀態當成新收到的狀態。
- 碼庫版本更換時可能需要重新配對，避免不同碼庫把同一候選序號解釋成另一個協議。

## 本版範圍與限制

- 每台 ESP32 配對控制一台冷氣，使用原廠 BC7215AC 程式庫提供的協議。
- 不承諾所有品牌、所有型號；同品牌也可能有多種協議。
- v1.0.6 提供配對後的擺風完整封包學習；不提供未知協議的通用按鍵回放或舒眠控制。
- 擺風樣本限同格式 1–3 段、合計及合併封包最多 255 bytes，詳見擺風操作說明。
- UI 列出的是通用控制項；冷專機不會因此具備暖房，實際能力以冷氣本身為準。
- 一次接收最多四段，每段最多 512 bytes；超過四段會拒絕處理。
- 紅外線為分時收發，發射期間無法同時接收；漏收會造成狀態不同步。
- 「本次已同步」及 HA 空調狀態都不是冷氣主機的確認回報；仍可能因遮擋、漏收、
  冷氣斷電而與實際不同。純電源切換碼在起始狀態未知時，也不能可靠推斷開或關。
- 沒有室溫感測器，因此只顯示設定溫度，不偽造目前室溫或壓縮機運轉狀態。
- 故障時停止空調發送、將 MOD 拉高喚醒模組，持續讀取原始 UART 資料。
  此時可用原廠遙控器觀察 RX 日誌，再按「重新檢查通訊」重新探測，無須重啟。
  故障模式的資料只作診斷，不會解析或更新 HA 空調狀態。重試不刪除已保存配對。

## 故障檢查

| 訊息／現象 | 檢查 |
|---|---|
| 探測未收到 UART 資料 | 表示探測視窗內軟體未讀到資料；仍需區分模組狀態、電氣路徑與時序，不能直接認定接線錯誤 |
| 收到 UART 資料但未確認 7A | 查看 `UART RX` 的原始十六進位資料 |
| BUSY 持續高逾時 | 記錄 GPIO1 電位、供電及當時模組狀態；診斷資訊不足以單獨判定接線錯誤 |
| UART 傳送完成檢查失敗 | `flush()` 逾時／失敗，不能認定 F7 00 已完整發出 |
| 沒有收到訊號 | 用紅外線空調遙控器；對準黑色接收頭、近距離測試 |
| 配對失敗 | 遙控器冷房25°C；短按風速鍵；仍失敗可能是碼庫尚未支援 |
| 配對成功但控制錯誤 | 嘗試下一個匹配，並保留收發日誌供分析 |
| C3 重啟 | 檢查供電，提供完整 ESPHome 日誌與重啟原因 |

## 從舊 Super Mini 遷移

1. 將 YAML 與完整 components 目錄放在同一資料夾，沿用自己的 secrets.yaml 三個項目。
2. 以 GPIO 標號接線，不以排針序號對照。BC7215A 供電維持 3.3V、共地。
3. 新板是不同硬體，有新的 MAC，舊板 Flash 中的配對與顯示狀態不會自動移過來；需重新配對。
4. 此包沿用裝置名稱 bc7215a-c3，替換時讓舊板斷電，避免同名公告。
5. 以新板實際取得的 IP 加入／重新設定 HA ESPHome 整合，API 連接埠 6053，這份 YAML 沒有 API 金鑰。
   相同 hostname 不保證 HA 自動把不同 MAC 的新板當成原裝置。

## 通訊診斷步驟（沿用 v1.0.1）

1. 更新完整 `components/bc7215a` 目錄。優先保留目前實際使用的 YAML，只在其 UART 區塊
   加上 `flush_timeout: 100ms`，並將本包的 `重新檢查通訊_RetryCommunication` 按鈕加入
   原有 button 區塊，lambda 內的元件 id 須對應現有 climate id（本包為 ac_controller）。
   本包 YAML 已依使用者提供的現行設定更新：API 僅設定 reboot_timeout、OTA 僅設定
   esphome 平台，AP 密碼引用 ap_password。secrets.yaml 只需 wifi_ssid、wifi_password、
   ap_password 三個項目；請沿用自己的值。
2. 設定使用 GPIO3 TX、GPIO2 RX、MOD GPIO0、BUSY GPIO1、19200 8N2。
3. 編譯檢查可使用 `esphome config bc7215a-c3.yaml` 及 `esphome compile bc7215a-c3.yaml`。
   本次不執行上傳；確認刷入後才進行以下實機流程。
4. 開機時不按原廠遙控器，查看 `PROBE F7 00`、`UART TX`、`UART RX` 與 `DIAG`。
   F7 00 是模組停機指令，不是空調關機指令。
5. 若故障，等待 MOD 回到高電位後短按原廠遙控器，查看是否出現 `UART RX`。
6. 停止遙控器發射，再按 HA「重新檢查通訊」。此按鈕僅在 FAULT 生效，不打斷發送或配對。
7. 重試收到 7A 後重新載入已保存的配對；若沒有有效配對則進入配對流程。已配對指示在
   故障期間暫為否，但匹配文字與保存資料仍保留；通訊恢復後需再次同步空調狀態。

`write-start delta` 是兩次軟體 write 呼叫的間隔，不能當作線上波形的精確間隔。
日誌在指令送完後才輸出，避免在 F7 與 00 之間插入記錄造成額外延遲。
每次記錄各方向最多 256 bytes，超出的診斷紀錄會明確顯示 omitted；正常解析仍使用
完整收到的資料。FAULT 的原始資料不送入碼庫解析。TX/RX 紀錄按方向分組，不代表逐字節交錯時序。

舊 Super Mini 的 COM3 已確認為原生 USB Serial/JTAG 日誌介面，並非 GPIO3／GPIO4 的 USB 透傳；
這個 COM 號碼與介面判定不能直接沿用到新板。舊板上次開啟串口出現 USB_UART_CHIP_RESET，
DTR/RTS 設為 false 也不能保證開啟時不重啟。
讀取日誌時應保留原始 bytes 並用 UTF-8 解碼。
